## 二、模块与调用关系

```
用户浏览器 ──HTTPS(/storage/*)──▶ nginx ──▶ cloud-app
                                              │  ① PortalJwtAuthFilter 本地验签门户 JWT（RS256 + JWKS 缓存）
                                              │  ② PortalShadowUserService 查/建 portal_user_map 影子用户
                                              │  ③ 出账时 PortalWalletClient 调门户扣费
                                              ▼
                                  门户 cloud-portal（内网 :3000）
                                              │
                                              ├─ 每 10 分钟拉 GET /api/internal/products
                                              └─ 支付后调 POST /api/internal/provision
```

**模块依赖**：`cloud-portal` → `cloud-auth` → `cloud-common`（与 `cloud-billing` 同一模式）。
`cloud-auth` 反向不依赖 `cloud-portal`，所以内网接口的密钥校验走独立的
`FilterRegistrationBean`（`InternalKeyFilter`，仅作用于 `/internal/*`，在 Spring Security 链之前短路）。

**为什么门户 JWT 过滤器放在 cloud-auth**：它必须挂在 `SecurityFilterChain` 内
（否则 `SecurityContextHolderFilter` 会清掉注入的认证），而该链由 `cloud-auth` 的 `SecurityConfig` 定义。

| 类 | 职责 |
|---|---|
| `PortalJwksClient` | JWKS 公钥缓存：启动拉取 + 12h 定时刷新 + **kid 未命中立即强刷** |
| `PortalJwtVerifier` | 校验 RS256 / `iss` / `exp`，拒绝 HS256 降级 |
| `PortalJwtAuthFilter` | 双令牌共存：本系统 HS256 令牌验签失败时兜底验门户 RS256 令牌 |
| `PortalShadowUserService` | 首达建档 + 唯一索引兜底并发 |
| `InternalKeyFilter` | `/internal/*` 的 `X-Internal-Key` 校验（定长比较，未配置即拒绝） |
| `PortalProductService` | 商品目录，一次全量、无分页、不做重计算 |
| `PortalProvisionService` | 开通幂等状态机（pending → granting → active） |
| `PortalBillService` | 先落库再扣费 / 退款，失败分流与退避重试 |
| `ReconciliationReportTask` | 每日对账上报（幂等，可补报） |
| `PortalSubscriptionExpireTask` | 到期 → 宽限 → 停机 |
| `PortalPostpaidBillingTask` | 按量后付出账（默认关闭） |

## 三、数据库变更（Flyway，PostgreSQL 方言）

指南给的是 MySQL DDL，已按本项目规范转换：`CHAR(36)`→`VARCHAR(36)`、
`DATETIME(3)`→`TIMESTAMPTZ`（与库内其它表统一，避免时区错位）、去掉 `ENGINE=InnoDB`、`COMMENT` 内联改 `COMMENT ON`。

| 迁移 | 模块 | 内容 |
|---|---|---|
| `V2020__portal_user_map.sql` | cloud-auth | `portal_user_map`（PK `portal_user_id` + UNIQUE `local_user_id`） |
| `V2021__portal_product_sku.sql` | cloud-portal | `portal_product_sku` + 4 个种子 SKU |
| `V2022__portal_provision.sql` | cloud-portal | `portal_provision` + **UNIQUE `order_item_id`**（幂等键） |
| `V2023__b_bill.sql` | cloud-portal | `b_bill` + 索引 + 账单号序列 `portal_bill_seq` |

> ⚠️ **号段说明（重要）**：本工程当前最大迁移是 `V2010`，但主干的 App 推送更新模块
> 已占用 `V2011` / `V2012`（见 commit `9dd2b17`）。为避免重演那次撞号，
> 门户接入**统一从 `V2020` 起编号**，把 `V2011`–`V2019` 留给尚未合并的主干迁移。

### 3.1 相对指南表结构的三处有意扩展（已在迁移注释中说明）

| 表 | 新增列 | 原因 |
|---|---|---|
| `b_bill` | `portal_user_id` | 指南 §6 的对账上报 payload 必填该字段，本表必须留存才能上报 |
| `b_bill` | `biz_date` / `fail_code` / `retry_count` | 对账按账期聚合；失败码与重试次数用于可观测性 |
| `portal_product_sku` | `quota_gb` / `sort_no` / `is_active` | `quota_gb` 是开通授予多少配额的**产品侧私有**信息（契约允许 `spec` 之外自留字段） |
| `portal_provision` | `last_billed_at` / `quota_reclaimed` | 按量出账去重标记 / 停机回收幂等标记 |

### 3.2 配额口径（需业务确认，见第五节）

开通授予配额写在 `users.quota_bytes`（即计费模块口径里的「免费额度」），**不动 `users.extra_bytes`**。

原因：`extra_bytes` 是 D 组计费模块的冗余列，由 `billing_records` 的
`ExpireTask` 在每日 03:00 重算（`recalcUserExpireAt` 会按 `billing_records` 覆写
`extra_expire_at`）。若门户开通也写 `extra_bytes`，会被 D 组的任务覆盖/清空，两边数据互相打架。
写到 `quota_bytes` 则不干扰 D 组，且上传配额判定 `used > quota_bytes + extra_bytes` 立即生效。

## 四、接口清单

### 4.1 内网接口（鉴权：`X-Internal-Key`，**须只监听内网**）

```http
GET /api/internal/products
X-Internal-Key: <平台侧下发的密钥>
```
```json
{
  "code": 0, "message": "ok",
  "data": { "products": [
    { "sku_id": "storage-500g", "name": "云存储·500G",
      "spec": { "quota_gb": 500, "transfer": "unlimited", "period": "30天" },
      "price_cents": 50000, "billing_mode": 1, "period_days": 30, "stock": null }
  ] }
}
```

```http
POST /api/internal/provision
X-Internal-Key: <密钥>
Content-Type: application/json

{ "order_item_id": 50001, "portal_user_id": "018f3a2b-...", "sku_id": "storage-500g",
  "quantity": 1, "period_days": 30, "extra": {} }
```
成功：`{"code":0,"data":{"instance_id":"st-000001","expire_at":"2026-11-08T02:00:00Z","quantity":1}}`
失败：`{"code":4003|4004|5001,"message":"...","data":null}` 且 **HTTP 状态码恒为 200**

| code | 场景 | 门户行为 | 本侧触发条件 |
|---|---|---|---|
| 4003 | sku 不存在/已下架 | 不重试，立即退款 | `portal_product_sku` 查不到或 `is_active=false` |
| 4004 | 库存不足 | 不重试，立即退款 | 有限库存 SKU 的原子扣减返回 0 |
| 5001 | 内部错误 | **重试最多 3 次**，用尽后退款 | 其它一切异常，含「开通进行中」 |

### 4.2 管理端运维接口（admin 鉴权）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/admin/portal/bills/charge` | 手工出账扣费（验证「先落库再扣费」；门户持续失败时最坏约 36 秒返回） |
| POST | `/api/admin/portal/bills/refund` | 退款（累计不得超原单金额） |
| POST | `/api/admin/portal/reconciliation/report?date=yyyy-MM-dd` | 手工补报对账（缺省昨天） |

### 4.3 定时任务

| 任务 | 默认 cron | 说明 |
|---|---|---|
| JWKS 刷新 | `0 0 */12 * * *` | 契约要求的 12 小时刷新 |
| 订阅到期扫描 | `0 0 4 * * *` | active → grace（宽限 7 天）→ expired + 回收配额 |
| 账单对账上报 | `0 0 6 * * *` | 上报前一日（status=1/2 的账单） |
| 按量后付出账 | `0 30 5 * * *` | **默认关闭**（`app.portal.postpaid.enabled=false`） |

## 五、⚠️ 上线前必须确认的三件事

1. **门户钱包接口路径与请求体字段名**
   指南正文只写了 `POST /wallet/deduct`、`POST /wallet/refund`，但对账接口明确是
   `/api/internal/reconciliation/report`。本实现把三个路径都做成可配置，默认值取：
   - `app.portal.wallet-deduct-path=/api/internal/wallet/deduct`
   - `app.portal.wallet-refund-path=/api/internal/wallet/refund`
   - `app.portal.reconciliation-path=/api/internal/reconciliation/report`

   **本侧实际发出的请求体（2026-10-09 用桩门户抓包实测，字段名待平台侧确认）**：

   ```json
   // POST {base-url}/api/internal/wallet/deduct      Header: X-Internal-Key
   {"bill_no":"storage-20261009-000002",
    "portal_user_id":"018f3a2b-7c1d-7000-9e21-3f9a2b8c1d00",
    "product_code":"storage","amount_cents":3000,"type":2}

   // POST {base-url}/api/internal/wallet/refund      Header: X-Internal-Key
   {"bill_no":"storage-20261009-000002",
    "refund_bill_no":"storage-20261009-000005",
    "amount_cents":3000,"reason":"verify full refund",
    "portal_user_id":"018f3a2b-7c1d-7000-9e21-3f9a2b8c1d00","product_code":"storage"}
   ```
   > 退款体里 `portal_user_id` / `product_code` 是按「便于门户溯源」附带的额外字段，
   > 若门户对未知字段严格校验（拒绝多余字段），需要去掉——这是唯一需要平台侧点头的地方。
   > `reason` 与 `refund_bill_no` 是契约 §4.4 明确要求的。
   >
   > `GET /.well-known/jwks.json` **不带** `X-Internal-Key`（契约里它是裸 JWKS 公开端点），实测确认。

2. **配额记账口径**
   开通把配额加到 `users.quota_bytes`（见 §3.2）。若团队希望走 `extra_bytes`
   与 D 组计费统一台账，需要先解决「D 组 `ExpireTask` 会按 `billing_records`
   覆写 `extra_expire_at`」的冲突，建议让 D 组把门户开通也写一条 `billing_records`。

3. **按量计费（billing_mode=2）的计价规则**
   真实规则（按实际用量 / 峰值 / 按天摊）尚未定义，因此
   `PortalPostpaidBillingTask` 默认关闭。当前实现的口径是「按 SKU 公示单价 × quantity，
   每个 `period_days` 出账一次」——**打开前请业务方书面确认**。

## 九、已知取舍与风险

| 项 | 说明 |
|---|---|
| 开通不写 `billing_records` | 门户开通走 `quota_bytes`，不在 D 组台账里；若财务要求统一台账，需与 D 组对齐（见 §5.2） |
| provision 非长事务 | 刻意为之：状态机每步立即提交，才能在崩溃/并发后被下一次重试正确观察。代价是极端情况下可能留下 `granting` 状态的行，需人工核对（日志有 `orderItemId`） |
| 手工出账接口可能耗时 | 门户持续系统失败时按 1s/5s/30s 退避，最坏约 36 秒。定时任务无此顾虑 |
| 现金/对账只上报 status=1,2 | status=0 的待扣账单门户侧无流水，上报只会制造噪声差异；其数量会打进日志便于发现 |
| 停机不删文件 | 只回收配额，用户已上传文件保留，留出续费恢复的人工窗口 |
| MySQL→PostgreSQL 转换 | 未做逐字对齐的只有 `TINYINT`→`SMALLINT`、`DATETIME(3)`→`TIMESTAMPTZ`；语义等价 |
